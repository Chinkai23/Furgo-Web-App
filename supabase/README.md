# Furgo development backend

This folder is the starting point for moving the prototype from browser-only demo data to shared online data.

## What the first migration sets up

- Supabase Auth signup creates a customer profile and active account status.
- Roles are stored separately as customer, staff, admin, or driver. The browser cannot grant itself a staff, admin, or driver role.
- Profile email and verified login phone are synced from Auth. Supplier profiles can edit their display name and contact phone, and store a private profile photo.
- Pet profiles, remarks, photo paths, and vaccination document paths are stored in Postgres.
- Pet photos and vaccination files go into a private `pet-records` Storage bucket.
- Row-level security restricts customer access to their own records and gives administrators support access.

## Connect a development project

1. Create a Supabase project for development and keep it separate from any future production project.
2. Apply the SQL migration files in numeric order using the Supabase SQL editor or Supabase CLI. The latest additions include the Marketplace Supplier Portal profile fields, photo storage, and public supplier cards; apply migrations not yet run in the project.
3. Configure email/password sign-in and Malaysian phone/WhatsApp OTP registration in Supabase Auth. The customer UI accepts local `01...` mobile numbers; convert them to `+60...` before sending them to Supabase Auth. WhatsApp OTP requires a supported provider (Twilio or Twilio Verify), a WhatsApp Business sender, an approved authentication template, and provider credentials.
4. The browser client is configured in `js/supabase.js` with this development project's URL and publishable key. A publishable key is safe to expose in a browser when Row Level Security is enabled. Never put a secret or service-role key in browser code.
5. Assign Executive, Manager, Director, and driver access through the protected portal process after matching accounts exist. All admin levels can open Admin Home, View Orders, Help, and the Activity Log; Executives see only Executive activity. Executives can view and manage orders, check customers in, and reply to customer enquiries. Managers also manage Promotions, Marketplace, Grooming, Pet Hotel, and Pet Daycare, can read the full activity log, and manage Executive accounts. Directors have all portal access, including Customers and Search Insights; they can manage Executive and Manager accounts, add another Director, and request peer Director removal after password verification. Every Director other than the requester and target who was active when the request was made must approve. One rejection stops the request. Requests that lose an unvoted approver are cancelled, and Directors see pending requests in the Admin navigation and Admin page. Email notifications are not configured; notices are in-portal only. Directors cannot edit peer Director access or remove their own access. The Admin page assigns access only to existing Furgo accounts, so the person must register before their email can be added.
6. Replace one feature at a time from local storage with Supabase reads/writes, beginning with sign-in, customer profile, and pet profiles.

## Current connection status

- Login and email/password registration use Supabase Auth. Malaysian phone/password login remains unavailable while the Phone Provider is disabled.
- Customer names and pet profiles are synchronized with Supabase. Pet photos and vaccination files use the private `pet-records` bucket.
- The `profiles` table holds customer name, email, and phone (`display_name`, `email`, `phone_e164`). Apply `0004_profile_contact_sync.sql` to copy the registration phone from Auth metadata and backfill existing accounts. `account_controls` intentionally contains status/admin-note fields only.
- Grooming settings, booking slots, and booking records use Supabase after `0002_grooming_bookings.sql` is applied. A database uniqueness rule prevents two active bookings from taking the same outlet/date/time slot; cancellation releases the slot.
- After `0003_shared_app_data.sql` is applied, QR tokens, driver-to-admin location updates, customer addresses and masked payment-method summaries, favorites/cart, demo Furgo Credit, admin product/offers/promotions, help details, and customer enquiries sync through the `app_data` table. Admin sessions load operational records across customer accounts; staff sessions load only order records; customer sessions load only their own records and shared catalog/settings. Supabase Realtime updates subscribed portals when those records change.
- After `0005_dedicated_service_orders.sql` is applied, Marketplace orders and line items, Pet Hotel bookings, and Pet Daycare bookings use dedicated tables. The migration copies matching records from `app_data`; the old rows remain there as a rollback/reference copy. Customer/admin reads are scoped by row-level security, and Realtime updates subscribed portals.
- After `0006_search_analytics.sql` is applied, submitted searches and selected search results are counted in Supabase without customer names, email addresses, phone numbers, or account IDs. Customers can insert search events, while only admins can read the aggregate insights returned by `get_search_analytics`.
- After `0009_admin_levels_and_audit.sql` and `0010_manager_permissions.sql` are applied, existing Admin accounts become Directors and existing Staff accounts become Executives. Directors and Managers can grant or remove access for lower-level users from their Admin page. The activity log records portal actions and can be read only by Managers and Directors.
- After `0013_director_product_service_insights.sql` is applied, Directors can view aggregated purchase timelines, product nutrition/ingredient information alongside sales, pet breed and weight-band summaries, service demand, and city/state or outlet activity. The database function checks Director access and returns no customer names, contact details, user IDs, or street addresses. Product nutrition data is snapshotted for new marketplace purchases; older order lines use the current catalog details when no snapshot exists. Nutrition values are descriptive catalog text, not normalized nutrient measurements.
- After `0014_director_vote_password_verification.sql` is applied, Director removal approvals appear only for votes awaiting that Director. Approve and reject actions request the account password and the database requires a fresh authenticated session before recording a vote.
- After `0015_admin_help_enquiries_and_executive_audit.sql` is applied, customer support requests are stored in `support_enquiries`. All admins can read and reply; customers can read only their own request and reply. Admin replies record the responder and timestamp for the portal inbox, while customer Help Center history omits the admin identity. Executive activity-log queries are restricted in the database to Executive actions; Managers and Directors retain the full log.
- After `0017_staff_checkin_token_access.sql` is applied, staff can read and update only the shared check-in token records needed to validate one-time customer QR/manual codes. The client formats ten-character codes as `XXXXX-XXXXX`, while lookup accepts either with or without the hyphen.
- After `0018_executive_marketplace_catalog_access.sql` is applied, Executive accounts can read and maintain Marketplace product catalog records. Marketplace offers and service setup remain restricted to Managers and Directors.
- After `0031_marketplace_supplier_portal.sql` is applied, Directors can link existing Furgo accounts to supplier records. Linked accounts sign in to the Marketplace Supplier Portal, submit products for Director approval, see rejection reasons, and view order lines assigned to their supplier. Approval publishes products to the shared Marketplace catalog; supplier order access is scoped by row-level security and a database function.
- After `0051_local_finder_community_directory.sql` is applied, customer Local Finder place submissions and edit suggestions enter a Manager/Director review queue; approved places publish to customers, admins can add and verify listings, and customer recommendations are counted without exposing recommender identities.
- After `0052_local_finder_source_attribution.sql` is applied, imported Local Finder records retain their source provider, per-place source link, and data license. CSV imports enter Pending Review and require an explicit positive pet policy; they remain private to customers until a Manager or Director approves them.
- After `0053_local_finder_admin_review_and_visibility.sql` is applied, Local Finder admin review is split into a summary dashboard, bulk review queue, and published-place manager. Managers and Directors can approve or reject multiple submissions together, edit, hide/unhide, verify, or delete published listings. Customer review decisions remain private.
- After `0055_local_finder_google_places_search_limit.sql` is applied and a browser-restricted Google Maps JavaScript API key is set in `js/google-maps-config.js`, customer and Manager/Director Local Finder forms use Google Places suggestions and Google Geocoding for reverse-address lookup and individual address-to-coordinate lookup. Enable Maps JavaScript API, Places API (New), and Geocoding API in the same Google Cloud project. The database atomically caps Google Maps service calls made by the share flow at 2,000 per Malaysia calendar month: each autocomplete search, selected place detail lookup, current-location reverse geocode, or fallback address geocode consumes one request; Share Now checks the remaining monthly quota before opening the customer form. CSV imports and admin batch backfills continue using Photon rather than Google Geocoding. Restrict the key by website referrer and enabled APIs, and set Google Cloud quotas and budget alerts separately.
- After `0032_marketplace_supplier_fulfillment.sql` is applied, suppliers see their own product submissions with approval results in the product list and can update tracking or delivery status for paid orders containing their products. Shipment details are stored per supplier, so one supplier cannot mark another supplier's part of a mixed order as shipped; the customer-facing whole-order status advances after every assigned supplier has fulfilled its part.
- After `0033_marketplace_supplier_catalog_reviews.sql` is applied, supplier listings are read from the active Marketplace catalog and scoped to the linked supplier. New products require Director approval; Directors see a pending-request badge on Admin Home, and rejected submissions show the Director's reason in the Supplier Portal.
- After `0034_supplier_instant_catalog_edits.sql` is applied, product text and image edits save immediately, while price, SKU, and variant changes wait for Director approval. Suppliers can hide, show, or delete their own listings immediately. The Supplier Portal includes Home, My Orders, Help, and Profile navigation.
- After `0035_marketplace_item_returns.sql` is applied, Marketplace checkout lines carry saved discount, paid-price, and shipping allocations. Customers can request a return for an individual delivered product within seven days and attach a photo; supplier decisions and Manager/Director escalation are recorded per product. Refund amounts use the saved paid amount plus that product's shipping allocation. Furgo's official receipt remains uploaded by Admin, and the workflow does not issue a payment or credit note; a Manager or Director records the refund as sent after handling it through the original payment method.
- After `0036_marketplace_cancellation_and_repayment.sql` is applied, customers can complete the prototype online payment within one hour, cancel an order before Furgo confirms it or a supplier ships it, and resubmit a rejected bank-transfer slip. Paid cancellations enter refund processing; Managers or Directors record the refund as sent after handling it through the original payment method. The online payment remains a demo and does not charge a card or wallet.
- After `0037_service_booking_cancellation.sql` is applied, customers can cancel Grooming, Pet Hotel, and Pet Daycare bookings until the order reaches `Received Order`. The database checks and updates the booking under a row lock, stores the customer's reason and status history, and records paid booking cancellations as Furgo Credit refunds.
- After `0038_service_payment_deadlines.sql` is applied, online payments for Grooming, Pet Hotel, and Pet Daycare get a one-hour deadline, Retry Payment action, and server-checked completion/expiry. A My Orders countdown updates while the page is open. When Supabase `pg_cron` is enabled, the migration also schedules a one-minute background sweep to cancel expired unpaid orders across Marketplace and services. Payment remains a demo action without a connected gateway.
- Development registration creates an email/password account and stores the entered phone number as profile metadata. Phone login is temporarily unavailable because Supabase requires an SMS provider whenever its Phone Provider is enabled. The phone is not verified in this temporary mode.
- Portal access is read from `portal_access`, with `user_roles` retained for the underlying order and customer-data policies. Do not use demo email shortcuts. Grant portal levels only through the protected team-management function after those Auth accounts exist.
- After `0045_supplier_profile_editing.sql` is applied, supplier users can save a profile name and contact phone and upload a cropped profile photo to their `supplier-profile-photos` Storage folder. Apply `0046_public_marketplace_supplier_profiles.sql` to show supplier company names and photos on customer product details, and let Directors view supplier account photos in the Admin supplier list.
- After `0047_marketplace_admin_product_freeze.sql` is applied, Admin freeze/unfreeze actions update the shared Marketplace catalog atomically, hide frozen products from customers, refresh supplier listings, and notify the assigned supplier.
- After `0048_marketplace_supplier_vouchers.sql` is applied, suppliers can create, edit, and delete their Shop Vouchers. Customers can view active offers separately from Furgo Vouchers and apply a seller voucher only to that supplier's products; Directors can inspect voucher details in each supplier account.
- After `0049_auto_generate_supplier_voucher_codes.sql` is applied, supplier voucher codes are generated from the supplier company name with a sequential suffix (for example, `petdaily01`) and are unique across suppliers.
- After `0050_supplier_free_shipping_vouchers.sql` is applied, supplier Shop Vouchers can use the Free Shipping type. It waives only that supplier's allocated share of the delivery fee; Admin Furgo free-shipping vouchers waive the order delivery charge while the Admin shipping threshold and fee remain separate settings.
- For this no-Twilio test stage, disable the Phone Provider in Supabase and keep Email enabled. Before production, configure Twilio or Twilio Verify, enable Phone Provider and Phone Confirmations, and restore the WhatsApp OTP registration step.

## Prototype and production boundary

`app_data` is a flexible JSON store for supporting prototype data, not a production order ledger. The three service order types now have dedicated tables, but order details and some uploaded receipt/slip files remain client-edited JSON. Hotel/daycare room capacity is not locked atomically in the database. Before accepting real payments or using check-in/status changes for operations, move sensitive transitions into server-side database functions and upload receipts/slips/banner images to Storage instead of storing their data in JSON. Furgo Credit remains demo-only and must never represent a cash balance. Payment gateways and WhatsApp OTP still need provider credentials. Customer-facing live driver location needs an order-linked location table and access policy; current live location sync is for Admin visibility only. Production QR verification should use a server-side function. Marketplace payment settlement/refunds are not connected to a payment provider; return/refund statuses are operational records only until that integration is added.
