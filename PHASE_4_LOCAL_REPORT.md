## Ownership and scope

The table is `public.app_data`. Each of these legacy settings is one global JSON document with `scope = 'shared'`, no owner, and the primary key `shared:<storage_key>:shared`. The previous admin writes replaced the entire document. That could overwrite another editor's changes or seed missing cloud rows from an old browser cache. There is no outlet or Store identifier on these rows. In the migrated schema, 0026's restrictive outlet policy blocks ordinary Staff/Managers from writing these global documents despite the earlier permissive policies. Legacy administrators with a Director rank can manage them. 0139 explicitly requires rank 3 and the existing `admin` role. Phase 4 adds no privileges for Managers, Executives, Store/Seller accounts, customers, or anonymous sessions. It preserves the existing read policies.

## Server and frontend behavior

`0139_version_shared_app_data.sql` adds an opaque UUID version and initializes existing canonical rows without changing payloads, keys, owners, scopes, or timestamps. A trigger replaces the version on privileged writes to those rows. The scoped RPC binds the request to the authenticated actor, checks the existing Director role, validates the allowlisted key and top-level JSON type, and makes the version check and update in a single SQL statement. An expected missing row uses insert-on-conflict with no replacement. Both cases return `PT409` when another writer wins. Restrictive RLS policies block authenticated direct inserts, updates, and deletes for these identities, including old upserts. An existing noncanonical row is preserved, but a reserved identity remains protected and any canonical ID collision requires review.

All eight editors bind their saves to the version available when the form is set up. The app reads authoritative settings separately from the general row-limited legacy query. Realtime notices trigger a coalesced reread rather than applying event payloads. An account change resets the shared cache and invalidates old editors. The server separately checks the actor in case the auth token changes around submission. Browser snapshots for the eight keys are preserved on disk for recovery, but normal settings reads and writes do not use them. A failed or conflicting save displays an error. An uncertain response requires a reload and verification before another edit. Replaying the original SQL version cannot apply the replacement twice.

Service banner uploads can finish before the settings save is confirmed. The editor keeps assets if submission may have committed, and it stops deleting previous image paths automatically. Unreferenced files may accumulate and require a separate reference-aware cleanup. When cloud settings cannot be read, existing built-in defaults can be displayed and the new client requires an authoritative baseline before updating an existing row.

## P1 recovery implementation and final local evidence

The signed-in channel treats Realtime notices as invalidations. On subscribe, rejoin, and browser reconnect it reads the protected Marketplace catalog and orders, service bookings, legacy rows, and authorized supplier contacts again. Notifications are batched and reads are serialized. Generation checks prevent pending results from one session publishing after sign-out or account change. Store and Seller use one route-scoped channel, with cleanup on route replacement and identity change. Store reloads the same RLS-scoped warehouse readers, and Seller reloads its existing RPC projections. Warehouse tables are not in the checked Realtime publication, so a visible Store inventory or Seller products/inventory screen also checks every 90 seconds. It suspends the periodic check for hidden tabs or an offline browser. Focus and reconnect trigger an immediate check. Current editors are skipped to avoid replacing a draft.

Protected mirrored business records are read from the current tab session and cleared on identity change. Existing disk snapshots remain available for separately approved recovery, and the app no longer imports them automatically into app_data, supplier contacts, or booking tables. The guest cart is separate from authenticated data and does not migrate into an account automatically. Other existing account-scoped features, such as pet-profile photos, still use their own paths. The new safeguards cannot undo a request already accepted by the server before sign-out.

Startup did contain direct seeding writes and a broad fallback that could present stale data. P1 removes that seeding and keeps another account's browser snapshots out of the view. Editing tracking unhides an inline form and focuses its courier field. An online, focus, or Realtime refresh can then replace the order list with `innerHTML`, discarding unsaved input. The local synthetic recovery harness does not exercise this real form. Preserve or defer refresh while the inline editor is dirty, and verify the actual DOM path before cutover. - **Previous P1 blocker, fixed locally — Marketplace reconciliation could show an incomplete snapshot at scale.** Each order, item, or return notification invalidates the whole orders group. The reader has no pagination, constructs one `in(order_id, …)` request for all visible orders, and replaces the cache with the returned rows. A hosted row limit can silently drop records or items. An oversized request can fail reconciliation. For ordinary events, review scoped invalidation. For reconnects, use bounded, paginated reads and do not replace state with a partial snapshot. Verify with data beyond an API page before cutover. See `js/app-data-sync.js` around lines 577–632 and 846–859.
